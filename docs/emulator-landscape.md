# MTG microcontroller emulation: what exists and what remains

Research date: **2026-10-10**. Scope: public primary sources for the 2024 Yin/Churchill microcontroller, related original-UTM simulators, and two existing general Magic engines. This is research and a proposed feasibility plan; no new emulator implementation, engine build, physical construction or execution test was performed for this document. Read alongside [research.md](research.md), [repositories.md](repositories.md) and [design.md](design.md).

## Finding

**I found an author-supplied programming-language interpreter and construction recipes, but no public completed rules-level emulator or documented physical execution of the 2024 microcontroller in the sources searched.** This is a bounded search result, not evidence that nobody has built one privately or published one under different terminology. Related projects already show the original UTM as cards, phases and narrated triggers; their specialized abstractions do not validate the new microcontroller. The most promising reuse candidate examined is **Forge**, because its source includes the text-changing setup cards as well as the gate ingredients. Support for their unusual combined interaction remains untested.

## Author artifacts and physical-build evidence

- The [author landing page](https://www.toothycat.net/~hologram/Magic/) links the paper, full manuscript, conference presentation, JavaScript simulator, detailed construction website and a song. Its inspected live HTML did not expose a second board simulator, GitHub repository, physical-build report or setup/execution video. The [construction explanation](https://cyh31.neocities.org/amepscimtg/explanation) supplies card recipes and terminology, including gates; its inspected HTML likewise did not link a board execution engine. These pages provide construction descriptions, not an independently executed rules trace.
- Dagstuhl's [official supplementary artifact](https://drops.dagstuhl.de/entities/artifact/10.4230/artifacts.22449) explicitly describes an interactive **JavaScript simulator of the programming language**, with register/memory highlighting and browser dialogs for input. It points to the same author simulator. Content creation is dated 2024-04-20; artifact publication is 2024-11-28. The historical “Inactive” status is qualified as being at publication; the simulator was reachable during this inspection.
- The [simulator JavaScript](https://www.toothycat.net/~hologram/Magic/MTGProgSimulatorText.js) implements `LanguageEngine`, twelve `BigInt` registers, a memory map and direct instruction dispatch. It does not execute a battlefield, combat declarations, continuous-effect layers, legal targets, priority or state-based actions. It is useful for expected ISA behavior and UI ideas, with the version/correctness cautions recorded in [research.md](research.md).
- The primary [FUN 2024 presentation](https://www.youtube.com/watch?v=x4uHhuUXEJo), uploaded 2024-06-17, labels 17:07 as its live demo. Around 17:08–17:28 the English automatic captions explain that manually checking programs led to writing a simple JavaScript simulator for the language. This supports identifying the demonstrated tool as the interpreter. Metadata and captions were inspected; video frames were not reviewed, so this document does not claim to have visually checked every slide or demonstration.
- The [published construction](https://drops.dagstuhl.de/storage/00lipics/lipics-vol291-fun2024/LIPIcs.FUN.2024.31/LIPIcs.FUN.2024.31.pdf) and [full manuscript](https://www.toothycat.net/~hologram/Magic/Magic_Microcontroller_full.pdf) describe a legally constructible game state, arithmetic gadgets, sample programs and a deck/setup recipe. Their references identify the language simulator. A proof of constructibility and a deck list should not be presented as a photographed physical build or independently replayed board execution. No such completed-build report was located through these references.

## Useful older board simulators, with concrete limits

**Snowman**, snapshot `5f74103`, has substantive board machinery. [Game.java](https://github.com/Snowman-s/Mtg-Turing-Machine/blob/5f74103/src/main/java/snowesamosc/mtgturing/Game.java) maintains a stack, triggered abilities, controller changes, attachments, replacement hooks, phased permanents and a state-based death pass. [Main.java](https://github.com/Snowman-s/Mtg-Turing-Machine/blob/5f74103/src/main/java/snowesamosc/mtgturing/Main.java) renders a selectable board and counters with Processing. However, `checkStaticAbility` collects specialized effects into subtype/P/T/protection sets; the inspected implementation does not supply the general layer/timestamp/dependency machinery needed for the new gate network. Its [Maven file](https://github.com/Snowman-s/Mtg-Turing-Machine/blob/5f74103/pom.xml) uses Processing 3.3.7, an old MTG Java SDK and OkHttp. It was read, not built; a screenshot or successful old-machine run would not establish new-machine correctness.

**Urza’s Universal Machine** was created on GitHub in March 2026; inspected snapshot `b35ba7fb38345125da0bd28f89185a06e34969e3` is dated 2026-03-20. Its [README](https://github.com/OmikronApex/Urzas-Universal-Machine/blob/b35ba7fb38345125da0bd28f89185a06e34969e3/README.md) explicitly simplifies to an infinite tape and infinite power/toughness for key support cards, and warns the setup is not quite tournament legal. Its [RogozhinMachine.py](https://github.com/OmikronApex/Urzas-Universal-Machine/blob/b35ba7fb38345125da0bd28f89185a06e34969e3/RogozhinMachine.py) derives token P/T from head distance and global adjustments, looks up the transition table directly during Infest, writes the next token, and emits frames narrating those events. Phasing is derived from machine state; victory checks the halt transition rather than independently deriving all Coalition Victory requirements. This is considerably more visual than a bare tape machine, but does not establish that every narrated event follows current Magic rules.

The same repository's [GadgetMachine.py](https://github.com/OmikronApex/Urzas-Universal-Machine/blob/b35ba7fb38345125da0bd28f89185a06e34969e3/GadgetMachine.py) describes a “2024 construction,” but initializes Alice/Bob/Charlie/Desdemona and Confusion in the Ranks/Donate/Peer through Depths. Its clock handler explicitly ends the step instead of completing a gadget transition; Donate selects the first token as a placeholder. This does **not** implement the published two-player Joraga/land reader architecture. It also lacks the `frames_for_next_step` implementation that the [web server](https://github.com/OmikronApex/Urzas-Universal-Machine/blob/b35ba7fb38345125da0bd28f89185a06e34969e3/web_server.py) calls, so the presence of that source file should not be advertised as a completed runnable new backend. The [license](https://github.com/OmikronApex/Urzas-Universal-Machine/blob/b35ba7fb38345125da0bd28f89185a06e34969e3/LICENSE) is CC BY-NC-SA 4.0; inspect its design before considering code reuse.

## Existing engines: established support versus unanswered integration

Engine snapshots below were selected at or before 2026-10-10 23:59:59 UTC. This avoids relying on a moving branch advancing into October 11 while researching. Source and complete recursive repository trees were inspected; neither engine was built or run with a microcontroller fixture.

### Forge: strongest inspected candidate

Forge has actual scripts for [Artificial Evolution](https://github.com/Card-Forge/forge/blob/5222f05e569da8e33c85858e6fe1698901548d64/forge-gui/res/cardsfolder/a/artificial_evolution.txt) and [Mind Bend](https://github.com/Card-Forge/forge/blob/5222f05e569da8e33c85858e6fe1698901548d64/forge-gui/res/cardsfolder/m/mind_bend.txt). [ChangeTextEffect.java](https://github.com/Card-Forge/forge/blob/5222f05e569da8e33c85858e6fe1698901548d64/forge-game/src/main/java/forge/game/ability/effects/ChangeTextEffect.java) asks for original/new words and applies persistent text changes with timestamps. This is a meaningful advantage over manually replacing the printed card with a custom implementation.

The inspected scripts also include [Dralnu’s Crusade](https://github.com/Card-Forge/forge/blob/5222f05e569da8e33c85858e6fe1698901548d64/forge-gui/res/cardsfolder/d/dralnus_crusade.txt), [Life and Limb](https://github.com/Card-Forge/forge/blob/5222f05e569da8e33c85858e6fe1698901548d64/forge-gui/res/cardsfolder/l/life_and_limb.txt), [Blood Sun](https://github.com/Card-Forge/forge/blob/5222f05e569da8e33c85858e6fe1698901548d64/forge-gui/res/cardsfolder/b/blood_sun.txt), [Dream Fighter](https://github.com/Card-Forge/forge/blob/5222f05e569da8e33c85858e6fe1698901548d64/forge-gui/res/cardsfolder/d/dream_fighter.txt), and [Halana and Alena, Partners](https://github.com/Card-Forge/forge/blob/5222f05e569da8e33c85858e6fe1698901548d64/forge-gui/res/cardsfolder/h/halana_and_alena_partners.txt). Blood Sun removes nonmana abilities, rather than indiscriminately removing every ability. [StaticAbilityContinuous.java](https://github.com/Card-Forge/forge/blob/5222f05e569da8e33c85858e6fe1698901548d64/forge-game/src/main/java/forge/game/staticability/StaticAbilityContinuous.java) handles type changes and ability removal; [GameAction.java](https://github.com/Card-Forge/forge/blob/5222f05e569da8e33c85858e6fe1698901548d64/forge-game/src/main/java/forge/game/GameAction.java) applies continuous layers and constructs a dependency graph, including dependency-loop handling. [PhasesEffect.java](https://github.com/Card-Forge/forge/blob/5222f05e569da8e33c85858e6fe1698901548d64/forge-game/src/main/java/forge/game/ability/effects/PhasesEffect.java) phases targeted game objects. Ingredient support is established; **correct interaction of the complete construction is not**.

There is already a [game simulation test harness](https://github.com/Card-Forge/forge/blob/5222f05e569da8e33c85858e6fe1698901548d64/forge-gui-desktop/src/test/java/forge/gamesimulationtests/BaseGameSimulationTest.java). Its [test controller](https://github.com/Card-Forge/forge/blob/5222f05e569da8e33c85858e6fe1698901548d64/forge-gui-desktop/src/test/java/forge/gamesimulationtests/util/PlayerControllerForTests.java) cannot be adopted unchanged for this task: absent a scheduled action it returns from attacker declaration; it picks a first item for many choices and returns the supplied simultaneous-trigger order. Those defaults could silently mask the very restrictions being tested. A dedicated controller must enumerate/validate runtime legal decisions, enforce required combat, record alternatives and reject unexplained choices. This is a concrete harness requirement, not a demonstrated bug in Forge's rules engine.

Forge uses [Java 17 and Maven](https://github.com/Card-Forge/forge/blob/5222f05e569da8e33c85858e6fe1698901548d64/pom.xml), and its repository is [GPL-3.0](https://github.com/Card-Forge/forge/blob/5222f05e569da8e33c85858e6fe1698901548d64/LICENSE). Treat engine redistribution, a fork and any copied code as explicit dependency decisions; a process adapter is an architectural seam, not a claim resolving licensing requirements.

### XMage: substantive general engine, concrete setup gap

XMage implements [Life and Limb](https://github.com/magefree/mage/blob/55531f539d4efe94408775c0184e1fbbf6a53c25/Mage.Sets/src/mage/cards/l/LifeAndLimb.java), [Blood Sun](https://github.com/magefree/mage/blob/55531f539d4efe94408775c0184e1fbbf6a53c25/Mage.Sets/src/mage/cards/b/BloodSun.java), [Dream Fighter](https://github.com/magefree/mage/blob/55531f539d4efe94408775c0184e1fbbf6a53c25/Mage.Sets/src/mage/cards/d/DreamFighter.java), [continuous-effect machinery](https://github.com/magefree/mage/blob/55531f539d4efe94408775c0184e1fbbf6a53c25/Mage/src/main/java/mage/abilities/effects/ContinuousEffects.java), and [phasing tests](https://github.com/magefree/mage/blob/55531f539d4efe94408775c0184e1fbbf6a53c25/Mage.Tests/src/test/java/org/mage/test/cards/abilities/keywords/PhasingTest.java). These should prevent dismissing it as an ISA-only simulator.

However, [Onslaught.java](https://github.com/magefree/mage/blob/55531f539d4efe94408775c0184e1fbbf6a53c25/Mage.Sets/src/mage/sets/Onslaught.java) comments out Artificial Evolution's card registration; the complete inspected tree contains no corresponding implementation class. Its [Dralnu’s Crusade](https://github.com/magefree/mage/blob/55531f539d4efe94408775c0184e1fbbf6a53c25/Mage.Sets/src/mage/cards/d/DralnusCrusade.java) hardcodes Goblin filtering and Zombie subtype addition. Therefore replaying the published text-edited setup cannot simply use the unmodified inspected card implementation. Supporting text-changing spells/effects, or injecting a prepared modified effect with a separately proved legal provenance, is required. The latter tests a prepared runtime fixture, not full legal setup execution. XMage's [license](https://github.com/magefree/mage/blob/55531f539d4efe94408775c0184e1fbbf6a53c25/LICENSE.txt) is MIT and its [Maven project](https://github.com/magefree/mage/blob/55531f539d4efe94408775c0184e1fbbf6a53c25/pom.xml) targets Java 8.

## Experiments needed before choosing a backend

The relevant authoritative baseline is the [Wizards Comprehensive Rules, 2026-09-25](https://media.wizards.com/2026/downloads/MagicCompRules%2020260925.txt), particularly layers/dependencies (613), triggers (603), replacement choices (616), hidden-zone costs for mandatory “if able” casting (118.8c), object identity (400.7) and phasing (702.26). Use these rules and a pinned Oracle snapshot, not whichever printed image a viewer displays.

| Experiment | Required evidence and likely work |
| --- | --- |
| Text-edited gate | Legally resolve Artificial Evolution on Dralnu and show the changed affected-type filter and added subtype, preserving timestamp and distinguishing text changes from copiable values. Forge has mechanisms; verify this actual card combination. XMage has the proven setup gap above. |
| Layered enable/disable | Derive type changes, Forest/Saproling interactions, resulting P/T and Blood Sun's ability removal. Test both gate states and multiple dependent gates; check whether relevant creatures lose their creature subtype when the construction removes creature status. Patch only a reproducible discrepancy against the rule derivation. |
| Phase out and return | Dream Fighter combat must phase the right objects out, disable their continuous effects and restore them at the correct untap with retained counters, text changes, attachments and timestamps. A boolean “enabled” switch is insufficient. |
| Forced targeting/combat | Enumerate legal targets, attacker/blocker configurations, optional effects and same-controller trigger orders. A controller choosing the intended target/order demonstrates one execution, not forced execution. If several orders are legal, show they converge to the same decoded state or repair the construction. |
| Program reader | Vaevictis must sacrifice/reveal the actual library cards, Wheel of Sun and Moon must move them appropriately, and all three combat reads must select X/Y/Z. Preload support state for the first fixture, but do not preload each instruction's result or directly toggle opcode gates. |
| End-to-end result | Begin with prepared `r1=2, r2=3`, program `Add [0,1,2]` then `HaltD [4,0,0]`. Require real reader, addition triggers and actual game outcome: a draw for HaltD. Then include NumBuild and Set so source literals, too, are generated by Magic execution. Compare decoded values to an independent ISA evaluator only after board transitions. |
| Bounded resource behavior | Reject numeric overflow and report supported bounds. Forge's [counter API](https://github.com/Card-Forge/forge/blob/5222f05e569da8e33c85858e6fe1698901548d64/forge-game/src/main/java/forge/game/card/Card.java) uses Java `int`; practical finite test success does not prove the mathematical unbounded-memory property. |

## Recommendation

Keep **Rust responsible for compilation, construction manifests, source mappings, comparison and trace/viewer interfaces**. First attempt a bounded Forge fixture through its real rules machinery and a strict instrumented player controller. This recommendation rests on inspected text-change/layer/phasing support; it is not an assurance that Forge already runs the microcontroller. Budget the experiment around the gate and reader/Add/halt acceptance evidence above, before committing to a full engine adapter.

If that experiment succeeds, an isolated Java runner can accept a versioned prepared-board/program description and produce events that Rust consumes. Initial events should carry stable object IDs, phase/active player, stack entries, legal-choice sets, targets, zone changes, phasing, counter changes and decoded values. The existing engine UI can help diagnose the fixture; the user-facing viewer should replay those events alongside source and instructions. Designing a runner is future work, not an existing ready API.

If it fails, retain the smallest failing fixture and classify the failure: unsupported setup card, inaccurate continuous-effect interaction, controller limitation, serialization limitation or construction ambiguity. Then decide between a narrow upstream engine patch and a specialized Rust rules subset. Avoid committing now to an entire general Magic engine. A specialized backend remains viable, but its card effects, layers, stack, combat and choices must independently derive the ISA result; emitting narrated Magic events after computing the ISA result repeats the abstraction gap in the older visual simulators.

A physical demonstration is a separate acceptance milestone: a current legal deck inventory, reproducible setup sequence including choices and timestamps, resulting board inventory, token/counter supplies and a printable short execution transcript. No physical completion is claimed by this research.

## Search and inspection record

Web searches included quoted combinations of `Magic microcontroller`, `MTGProgSimulator`, `amepscimtg`, `A Programming Language Embedded in Magic`, the author names, and `github`, `simulator`, `emulator`, `physical`, `built` and `played`. Followed the published paper's primary references, author landing-page links, supplementary artifact, detailed live explanation and conference presentation metadata/captions. Exact GitHub repository API searches for `"Magic microcontroller"`, `"MTGProgSimulator"` and `amepscimtg` returned no repositories; the broader MTG/microcontroller search returned an unrelated life tracker. Repository search indexes names/descriptions/readmes rather than every source file, so these negative results are limited.

Inspected source, README and manifests for Snowman and Urza; complete recursive file trees and selected card/core/test sources for Forge and XMage. Did not search private repositories, contact authors, inspect every public branch, watch every video frame, or run complete engine card suites. These limitations are why the conclusion is “no completed public 2024 board implementation found in this search,” not “none exists.”
